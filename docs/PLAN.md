# PLAN — 영상회의 코덱 통합 제어 앱 개발 계획서

- 문서 버전: v1.0
- 작성일: 2026-07-28
- 연관 문서: `PRD.md`, `SPEC.md`, `PIPELINE.md`
- 진행 방식: 1인 개발자, 바이브 코딩 — 각 Phase는 작게 나눠 실행 가능한 형태로 완성 후 검증, 다음 단계로 진행. 고정 일정(날짜)보다 "완료 조건(DoD)" 충족 여부로 진행 판단.
- 코드 수정(기능 추가/버그 수정) 시 테스트→QA→버전/태그→배포 절차는 `PIPELINE.md`를 따른다 — 특히 버그 수정 후 fix 버전을 낼 때는 이 문서의 진행 판단과 별개로 `PIPELINE.md` §2~§4를 반드시 거친다.

## Phase ① — 시뮬레이터 + 접속/파싱 코어

**목표**: 실장비 없이도 전체 드라이버 로직을 검증할 수 있는 기반을 만든다.

- [ ] 프로젝트 구조 셋업 (`app/`, `requirements.txt`, 가상환경)
- [ ] `DeviceDriver` 추상 인터페이스 정의 (`core/driver_base.py`)
- [ ] Poly Integrator Reference Guide(Group/HDX)에서 필요 명령(상태조회/mute/dial/hangup/reboot/캘린더) 확인 및 `poly_commands.py` 상수화
- [ ] Poly 모의 서버(`poly_sim_server.py`, Telnet 우선) 구현 — 상태 유지, 명령별 응답 반환
- [ ] `PolyDriver` 구현 (telnetlib3 기반) + 응답 파서
- [ ] Cisco API Reference Guide에서 xAPI 명령(xStatus/xCommand) 1차 확인 및 `cisco_commands.py` 상수화 (대상 모델 확정 필요 — 오픈 이슈)
- [ ] Cisco 모의 서버(`cisco_sim_server.py`, SSH) 구현
- [ ] `CiscoDriver` 구현 (paramiko 기반) + 응답 파서
- [ ] 단위 테스트: 각 드라이버 메서드가 시뮬레이터 대상으로 정상 동작하는지 검증

**완료 조건(DoD)**: 두 드라이버 모두 시뮬레이터를 대상으로 connect/get_status/mute/dial/hangup/reboot 호출이 예외 없이 동작하고, 상태 변화가 시뮬레이터에 반영됨을 테스트로 확인.

## Phase ② — 레지스트리 + 대시보드 MVP

**목표**: 여러 장비를 등록하고 한 화면에서 상태를 보고 기본 제어를 할 수 있는 MVP.

- [ ] `CredentialVault` 구현 (Windows DPAPI 암호화/복호화)
- [ ] 장비 레지스트리 저장/조회 (`core/registry.py`, 암호화된 JSON)
- [ ] FastAPI 앱 스캐폴딩 (`app/main.py`) + 정적 UI 서빙
- [ ] REST API: 장비 CRUD (`/api/devices`)
- [ ] `PollingScheduler` (asyncio, Semaphore 기반 동시성 제한) 구현
- [ ] WebSocket 상태 브로드캐스트 (`/ws/status`)
- [ ] 대시보드 UI: 장비 카드/테이블, 상태 뱃지(온라인/통화중/음소거/오류)
- [ ] 장비 등록/수정 UI (폼)
- [ ] 개별 제어 UI: mute/unmute, dial, hangup, reboot(확인 다이얼로그 포함)
- [ ] 시뮬레이터 장비 다수(예: 5~10대) 등록 후 대시보드 통합 테스트

**완료 조건(DoD)**: 시뮬레이터 장비 여러 대를 등록해 대시보드에서 상태가 실시간(폴링 주기 내)으로 갱신되고, UI에서 제어 명령이 정상 반영됨을 확인.

**✅ 2026-08-04 DoD 충족 확인.** 2026-08-04 VDI 라운드에서 발견된 이슈 2건(Cisco Teams 목록

## Phase ⑦ — 공개 배포/상업화 (향후, 착수 여부 미정)

**주의**: 현재 PRD의 목표·비목표는 "사내 1인 개발자용 내부 도구"를 전제로 한다. 이 Phase는
그 전제가 바뀌어 **일반에 공개하거나 유료로 판매하기로 실제로 결정했을 때만** 착수하는
별도 트랙이며, 지금 진행 중인 Phase①~⑥과는 순서상 무관하다 (선행 조건 아님). 2026-07-29
논의 내용을 착수 체크리스트로만 남겨둔다 — 실제 착수 시점에 세부 사항 재확인 필요.

- [ ] **코드 서명 인증서 발급** — OV로 시작 권장(EV는 2024-03 이후 SmartScreen 즉시신뢰 혜택이
      사라져 OV 대비 이점이 줄어듦). 2023-06 이후 정책상 하드웨어 토큰/클라우드 HSM 필수이므로
      로컬 .pfx 서명 방식은 불가. 신규 게시물은 초기 SmartScreen 경고를 다운로드량으로 평판을
      쌓아 해소해야 함(서명해도 즉시 사라지지 않음).
- [ ] **오픈소스 라이선스 고지** — FastAPI/uvicorn/paramiko/telnetlib3/pywin32/Jinja2/Alpine.js
      등 번들 의존성 라이선스(대부분 MIT/BSD/Apache) 확인 및 배포물에 고지문 포함.
- [ ] **상표권 주의** — "Poly", "Cisco" 명칭을 마케팅에 쓸 때 공식 파트너/인증 오인 소지 없는
      표현으로 제한 ("Poly/Cisco 코덱 호환" 등).
- [ ] **사업자 등록** — 유료 판매 시 필요.
- [ ] **이용약관/책임 제한(EULA)** — reboot 등 파괴적 원격 명령을 포함하므로 오작동 책임 제한
      조항 포함 검토.
- [ ] **라이선스 키/결제 체계** — 현재는 사용 제한 로직이 전혀 없음. 유료화 시 키 검증 또는
      구독 체계 추가 필요.
- [ ] **백신사 오탐 관리** — 서명 이후에도 PyInstaller 특성상 일부 백신 오탐 가능. Microsoft
      등 주요 백신사에 샘플 사전 제출해 화이트리스트 등록 검토.

## 진행 원칙

1. 각 Phase는 이전 Phase의 DoD 충족 후 착수한다.
2. 불확실한 제조사 명령은 반드시 공식 문서를 재검색해 확정한 뒤 구현한다 (추측 금지 — 프로젝트 지침).
3. 매 작업 단위는 "실행 가능한 완성 코드" 형태로 제공하고, 작게 나눠 검증한다.
4. 보안(DPAPI 암호화, 평문 금지, 폴링 오탐 회피)은 모든 Phase에서 공통으로 지켜야 하는 제약으로 취급한다.
5. 코드 수정 후 버전을 올리고 배포하는 절차는 `PIPELINE.md`를 따른다 (자동 테스트 통과 → 수동 QA 체크리스트 → CHANGELOG/버전/태그 → exe 재빌드/배포 → 사후 로그 모니터링).
