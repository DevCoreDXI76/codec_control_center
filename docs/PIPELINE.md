# PIPELINE — 개발/테스트/QA/릴리즈 절차

- 문서 버전: v1.0
- 작성일: 2026-07-29
- 연관 문서: `PLAN.md`, `SPEC.md`, `CHANGELOG.md`, `SCHEDULE.md`
- 목적: 코드 수정(기능 추가/버그 수정)이 생겼을 때 "무엇을 어떤 순서로 확인하고 버전을 올려야
  하는가"를 매번 즉흥적으로 판단하지 않도록 고정된 절차로 남긴다. 1인 개발(+ Claude 협업),
  단일 EXE 사내 배포라는 프로젝트 규모에 맞춰 업계 표준 파이프라인(빌드→테스트→QA→릴리즈→배포→
  모니터링)을 축소한 것이다 — 스테이징 서버, 블루/그린 배포, 별도 QA팀 같은 개념은 이 규모에
  맞지 않아 의도적으로 포함하지 않았다.

## 1. 전체 흐름 요약

```
코드 수정 → ② 자동 테스트(pytest 전체 통과) → ③ 수동 QA(체크리스트)
→ ④ 버전/릴리즈(CHANGELOG + 버전 올림 + git tag) → ⑤ 배포(exe 재빌드, 이전 exe 보관)
→ ⑥ 사후 모니터링(data/app.log 확인)
```

**규칙: ②를 통과하지 못하면 ③으로, ③을 통과하지 못하면 ④로 진행하지 않는다.** 각 단계는
이전 단계가 끝난 뒤에만 시작한다.

## 2. 자동 테스트 (CI 역할)

- 코드를 수정했으면 예외 없이 `pytest -q`(현재 205개, 프로젝트 루트에서 `.venv`로 실행)를
  전체 통과시킨다. 실패한 테스트가 하나라도 있으면 다음 단계로 넘어가지 않는다.
- 새 기능/버그 수정에는 반드시 그 동작을 검증하는 테스트를 같이 추가한다(이미 지켜온 방식 —
  구조·문서화용이 아니라 회귀 방지가 목적).
- (선택, 필수 아님) GitHub Actions로 `push`할 때마다 자동으로 pytest를 돌리는 워크플로를
  추가할 수 있다 — 사람이 로컬에서 깜빡 잊고 못 돌린 경우의 안전망 역할. 지금은 Claude가
  매번 직접 실행해 결과를 보여주는 방식으로 충분해 아직 구성하지 않음.

## 3. 수동 QA 체크리스트

자동 테스트는 시뮬레이터 기준이라 실제 네트워크/실장비 동작까지는 보장하지 않는다. 새 exe를
"릴리즈 가능"으로 표시하기 전에 아래를 최소 1회 훑는다 (실장비가 없으면 시뮬레이터 대상으로,
VDI 반입 후에는 실장비 대상으로).

VDI/실장비 대상 라운드는 이 체크리스트만으로는 환경 정보·결과·발견 이슈를 남기기 부족하므로,
`docs/field_tests/YYYY-MM-DD_vX.Y.Z_VDI.md` 형식으로 별도 기록한다(최초 예시:
`docs/field_tests/2026-07-31_v1.3.0_VDI.md`). 다음 라운드에는 그 파일을 복사해 재사용한다.

- [ ] exe 실행 → 브라우저 자동 오픈 → 대시보드 정상 로드
- [ ] 장비 신규 등록 → 카드가 뜨고 상태가 "미확인"에서 정상적으로 갱신됨
- [ ] Mute/Unmute 클릭 → 버튼 상태와 실제 장비 상태가 일치
- [ ] Dial/Hangup 동작 (가능한 환경에서만; 실장비면 저위험 명령부터)
- [ ] Reboot은 신중하게 — 실제 회의실 장비 대상으로는 사용 시간 외에만 테스트

- [ ] `data/app.log` 파일이 생성되고, 의도적으로 실패시킨 동작이 로그에 남는지 확인

## 4. 버전/릴리즈 규칙

### 4.1 버전을 언제 올리는가 (SemVer)

`app/__version__.py`의 버전을 다음 기준으로 올린다:

| 변경 성격 | 버전 자리 | 예시 |
|---|---|---|
| 기존 기능을 깨뜨리는 큰 구조 변경 (현재 규모에서는 거의 없음) | MAJOR (X.0.0) | — |
| 새 기능 추가 (Phase 완료, 새 API/화면 등) | MINOR (1.X.0) | SSH 트랜스포트 추가 → 1.1.0 |
| 버그 수정, 문서/로깅 개선 등 기존 기능 범위 내 수정 | PATCH (1.0.X) | — |

### 4.2 버전을 올릴 때마다 반드시 같이 하는 것

1. `app/__version__.py`의 `__version__` 값 갱신 (상단 docstring에 무엇이 바뀌었는지 한 줄 요약)
2. `CHANGELOG.md`에 `## [X.Y.Z] - YYYY-MM-DD` 항목 추가 (Keep a Changelog 형식: Added/Changed/Fixed/Known Issues)
3. **`git tag vX.Y.Z` 태그 생성** — 지금까지 이 부분이 종종 빠졌던 지점이다(v1.0.0/v1.1.0 미태그로 확인됨). 버전을 올린 커밋에는 반드시 같은 버전의 태그를 붙인다.
4. 커밋 → (사용자 요청 시) `git push` + `git push --tags`

## 5. 배포 (exe 재빌드/교체)

- `pyinstaller build.spec` 재빌드 → `dist/CodecControlCenter-vX.Y.Z.exe` 생성.
- **이전 버전 exe는 즉시 지우지 않고 최소 1개는 보관한다** — 새 버전에 문제가 생기면 바로
  이전 exe로 되돌릴 수 있도록(수동 롤백). `dist/`는 `.gitignore` 대상이라 git에는 안 남으므로
  로컬/사내 파일 서버 등에 별도 보관 위치를 정해둔다.
- exe만 교체하고 `data/` 폴더는 그대로 유지한다 (SPEC.md 11절 — 이미 지켜지고 있는 규칙).
- exe 전달은 Gmail 첨부 금지, 사내 승인된 전송 경로만 사용한다 (SPEC.md 11.1절).

## 6. 사후 모니터링

- 새 버전을 실제 회의실에 배포한 뒤 며칠간은 `data/app.log`를 주기적으로 확인한다 —
  특히 버그 수정(fix) 릴리즈 직후에는 같은 문제가 재발하지 않는지 이 로그로 확인한다.
- 문제가 재발하면 §2로 돌아가 사이클을 다시 시작한다 (문제 재현 → 테스트 추가 → 수정).

## 7. 일일 작업 기록 (Notion 동기화)

이 프로젝트는 Notion "AI 비서 집무실"(데일리 로그/계획/업무 DB)과 별도 "Vibe Coding Study"
워크스페이스의 Tasks DB(커밋 자동 기록용)를 함께 쓴다. 둘 다 사람이 매번 기억해서 열어보지
않아도 최신 상태를 유지하도록 아래 절차를 **매 작업 세션마다** 거친다.

### 7.1 커밋 단위 — 자동 (기존 `post-commit` 훅)

- 커밋할 때마다 `.notion/scripts/git-hooks/notion_task_logger.py`가 자동 실행되어 Notion
  Tasks DB(`fa8ae175bcb34392ad27abc70be6c24e`)에 커밋 1건당 1개 항목을 기록한다. 사람이 따로
  할 일은 없다 — 단, 아래 두 경우 조용히 실패할 수 있으므로 **커밋 직후 출력에 `❌`가 없는지
  확인**한다(훅 실패해도 커밋 자체는 항상 성공하므로 놓치기 쉽다):
  - 워크트리(`.claude/worktrees/<name>/`)에서 커밋한 경우 — `.env`가 gitignore 대상이라
    워크트리 체크아웃에는 없어서 `NOTION_PROJECT_PAGE_ID`를 못 찾고 스킵된다.
  - 훅을 실행하는 `python`/`py`가 `requests`를 못 찾는 경우 — 2026-07-31부로 `requirements.txt`에
    `requests` 추가 + 프로젝트 `.venv`에 설치해 기본 해결됐지만, 다른 인터프리터로 실행되면
    재발할 수 있다.
- 위 두 경우로 누락된 커밋을 발견하면 **메인 저장소 루트**(`.env`가 있는 곳)에서 아래로
  일괄 백필한다:
  ```
  python .notion/scripts/git-hooks/notion_task_logger.py . --backfill <hash1>,<hash2>,...
  ```

### 7.2 세션/하루 단위 — Claude가 마무리 시점에 수행

사용자가 "오늘은 여기까지", "하루 마무리해줘" 등으로 작업을 마치거나, 명시적으로 요청하면
Claude는 그 세션에서 실제로 한 일을 근거로 아래를 갱신한다(빈 템플릿을 채우지 않고, 실제
커밋/변경 사항에서만 끌어온다):

1. **데일리 로그 DB**: 오늘 날짜 항목이 있으면 "오늘의 Top3"에 이어서 추가(덮어쓰지 않음),
   없으면 새로 생성. 트러블슈팅/교훈이 있으면 "회고"에 반영.
2. **계획 DB**: 오늘 해소된 리스크, 목표일이 실제 진행 속도와 달라진 마일스톤을 갱신. 새로
   생긴 리스크/마일스톤이 있으면 추가.
3. **업무 DB**: 다음 세션(특히 다음 날)에 할 구체적 작업이 있으면 날짜·상태("시작 전")로 등록.
   이미 끝난 업무는 "완료"로 표시.
4. **프로젝트 DB 설명**: 위 갱신과 크게 어긋나면(오래돼 최신 상태를 안 보여주면) 함께 갱신.
5. **§7.1의 Tasks DB 누락 여부**도 이 시점에 한 번 확인 — 세션 중 만든 커밋이 전부 기록됐는지.

이 항목들은 실제로 코드를 바꾼 게 없어도(문서만 갱신했어도) 수행한다 — 목적이 "코드 변경
이력"이 아니라 "오늘 무엇을 했고 내일 뭘 할지"를 사람이 Notion만 봐도 알 수 있게 하는 것이기
때문이다.
